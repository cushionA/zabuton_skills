# Simple Plan Auditor

## 目的

このSkillは、計画を実行者向けの長大なTODOではなく、**人間が短時間で監督できる作業アーティファクト**として構成する。

重視するのは技術選定の細部ではなく、次の三点である。

1. 全体を見ただけで、作業の流れと重要な確認事項を把握できること。
2. 論理的に必要な作業・判断・検証が欠落していないこと。
3. 気になる工程だけを展開し、具体手順まで追跡できること。

計画は必ず **全体 → 工程 → 詳細** の順で提示する。

## 適用対象

次のような依頼で使用する。

- 新規機能、変更、移行、調査、運用変更の計画作成
- 長大なPLAN.mdの再構成
- AIが作成した計画の監査
- 複数工程・複数コンポーネントにまたがる作業の整理
- 実行前に手順漏れ、依存漏れ、確認漏れを検出したい場合
- 一度提示・承認された基準版Planへ後続の変更指示や要件変更を反映し、何を直したか短時間で確認したい場合

単純な1〜3手順の作業には使用しない。

# 1. 中核原則

## 1.1 Progressive Disclosure

計画は三層で構成する。

- **L0: 全体作業マップ** — 計画全体を監督するための層
- **L1: 工程詳細** — 気になった工程を展開する層
- **L2: Task詳細** — 実行に必要な具体手順を確認する層

L0へすべてのTaskを載せない。

大規模な計画でL0が肥大化する場合は、**複数作業を同一セルへ詰め込むのではなく、L0へ載せる作業自体の抽象度を上げる。** 詳細はL1へ降ろす。

重要な確認事項は粒度調整のために削除しない。

## 1.2 Work Map First

L0の中心は **全体作業マップ** とする。

標準形は三列とする。

| 工程 | 主な作業 | 確認事項 |
|---|---|---|
| ... | ... | ... |

- **工程**: 作業を分類する上位区分。重複してよい。
- **主な作業**: 人間が抜けの有無を判断したい作業。1行につき1作業とする。
- **確認事項**: その作業が論理的に成立するために確認すべき条件。

工程名を一意にする必要はない。同じ工程に複数作業がある場合は、工程名を繰り返す。

## 1.3 Check First

このSkillの主役は **確認事項** である。

技術的な細部はAIへ委ねてよいが、論理的に確認が必要な事項は省略してはならない。

特に以下は、該当する限り必ず確認対象に含める。

- 現行仕様・既存挙動の把握
- 影響範囲と依存関係
- 実装前に確定すべき判断事項
- 作業順序と開始条件
- 成果物が実際の利用経路へ組み込まれること
- 正常系、異常系、中断、部分成功
- 再実行・重複実行
- 既存機能への回帰影響
- データ・状態の移行
- 新旧切替と切り戻し
- 旧資産・暫定対応の撤去
- 運用・引き継ぎ
- 最終状態が目的と一致すること

確認事項が本当に存在しない場合も空欄にしない。**`なし` と明示する。**

空欄は「確認漏れ」と区別できないため禁止する。

## 1.4 Human Review Granularity

粒度は実装単位ではなく、**人間が「この作業は抜けていないか」を判断できる単位**で決める。

L0へ載せる候補:

- 現行把握・影響分析
- 要件・方針確定
- 主要変更
- 既存経路への組み込み
- データ移行
- 統合検証
- 切替
- 運用移管
- 旧資産・暫定対応の撤去

L0へ載せない細粒度の例:

- 個別関数の実装
- 1ファイル単位の編集
- ライブラリAPIの呼び出し方法
- 型定義の細部

これらは必要に応じてL1/L2へ置く。

## 1.5 One Work Item Per Row

主な作業は1行1作業とする。

良い例:

```markdown
| 現行把握・影響分析 | 現行の利用フローを整理 | 見落としている利用経路がないか |
| 現行把握・影響分析 | 依存先と共有データを整理 | 暗黙の依存関係が残っていないか |
```

避ける例:

```markdown
| 現行把握・影響分析 | 現行フロー / 依存先 / 共有データ / 変更影響を整理 | ... |
```

大規模計画では行を詰めるのではなく、L0の作業表現を一段上位化する。

## 1.6 Flow and Wiring

「作成」「実装」で工程を終わらせない。

常に次の連鎖を確認する。

```text
前提整理
  ↓
実装・変更
  ↓
既存経路への組み込み
  ↓
統合検証
  ↓
移行・切替
  ↓
運用確認
  ↓
撤去・最終確認
```

成果物を作成しても、利用経路への接続や切替が計画されていなければ未完了とみなす。

## 1.7 Unknown Is Valid

未確定事項を推測で補完しない。

以下を明示的な状態として扱う。

- 未決定
- 要確認
- 仮定
- 外部依存
- ブロッカー
- 人間判断が必要

重要なものは `要注意事項・人間判断` へ昇格する。

## 1.8 Revision Traceability

`今回の修正` は、**一度提示・承認され基準版になったPlanに対する後続変更**を人間が追跡するために使う。

Step 11のPlan Auditで見つかった問題を直す作業は、Plan作成プロセスそのものに含まれる。したがって、**Plan Audit由来の修正は `今回の修正` に載せず、`R1`, `R2` なども付けない。** 監査修正は完成版へ自然に織り込む。

基準版Planへ人間の追加指示、要件変更、前提変更などを反映するときは、修正前Planと比較し、意味が変わった箇所だけを `今回の修正` としてPlan先頭に示す。単なる言い換え、表記揺れ、読みやすさだけの変更は原則として修正項目に含めない。

追跡対象は次とする。

- 作業の追加・削除
- 作業順序の変更
- 依存関係・分岐の変更
- 確認事項の追加・削除・意味変更
- 人間判断・前提・ブロッカーの変更
- 移行・切替・切り戻し・復旧条件の変更
- 完了条件や次工程への接続の変更

各変更へ `R1`, `R2` ... のIDを付け、修正版Planの対応箇所へ `[R1]` のように付記する。

`R` IDは**今回の修正を読むための一時的な参照**であり、恒久的なTask IDや履歴台帳にはしない。修正版が承認され新しい基準版になったら、次回の修正ではIDを振り直してよい。

修正サマリの標準形:

```markdown
## 今回の修正

| ID | 種別 | 対象 | 修正内容 | 理由 |
|---|---|---|---|---|
| R1 | 確認事項追加 | 一括登録 | 再実行時の重複防止確認を追加 | 部分失敗後の再実行を安全にするため |
| R2 | 順序変更 | 本番導入 | DB移行をアプリ切替より前へ移動 | 新旧スキーマの不整合を防ぐため |
```

修正版Plan側:

```markdown
| 一括登録 | 再実行・重複実行の扱いを適用 [R1] | 同じ操作の再実行で二重登録が発生しないか |
```

基準版への後続変更が意味上存在しない場合は `今回の修正: なし` と明示し、無理に差分を作らない。

# 2. L0構成

全体概要は次の順序を基本とする。

1. **目的**
2. **全体作業マップ**
3. **要注意事項・人間判断**
4. **重要な依存・分岐**

`重要な依存・分岐` はL0の最後に置く。

独立した「完了条件」セクションはL0に置かない。目的達成に必要な最終確認は、全体作業マップの作業・確認事項およびL1の検証へ織り込む。

詳細な書式は [references/PLAN_FORMAT.md](references/PLAN_FORMAT.md) を使用する。

# 3. 表現ルール

公開用の計画書として自然な日本語を使う。

見出しは名詞句、作業欄は簡潔な業務表現を基本とする。

例:

- `現状調査` → `現行把握・影響分析`
- `現状と影響範囲を確認` → `現行フローと変更影響を整理`
- `土台を作る` → `共通基盤を整備`
- `失敗ケースを潰す` → `異常系・再実行条件を検証`
- `壊れていないか確認` → `回帰影響を検証`
- `戻す方法` → `切り戻し手順`
- `後片付け` → `旧資産・暫定対応の撤去`

口語的・幼く見える表現を避ける。ただし難解な官僚文にはしない。

# 4. 作成ワークフロー

## Step 1: 目的を固定する

1〜3文で、作業完了後に何が可能になるか、何が変わるかを書く。

## Step 2: 必要作業を洗い出す

詳細度を気にせず、目的達成までに必要な作業を列挙する。

監査観点は [references/AUDIT_RULES.md](references/AUDIT_RULES.md) を使用する。

## Step 3: 各作業へ確認事項を付与する

各作業について、実施内容より先に次を考える。

- 何が成立していなければこの作業は失敗か
- 前後工程との接続に抜けがないか
- 重要な分岐・失敗・再実行条件は何か
- 既存状態へどのような影響があるか
- 人間が事前に判断すべき事項は何か

確認事項がなければ `なし` とする。

## Step 4: L0用に粒度を調整する

L0が大きくなりすぎる場合、複数作業を1セルへ束ねない。

代わりに、L0へ載せる作業自体を上位化する。

集約してはいけないもの:

- 重要な判断が異なる作業
- 重要な正常系・異常系の分岐
- 移行・切替・切り戻し
- 独立した外部依存
- 高リスクなデータ・状態変更
- 人間が個別に監督すべき作業

## Step 5: 全体作業マップを作る

三列表を作る。

```markdown
| 工程 | 主な作業 | 確認事項 |
|---|---|---|
| 現行把握・影響分析 | 現行の利用フローを整理 | 見落としている利用経路がないか |
| 現行把握・影響分析 | 依存先と共有データを整理 | 暗黙の依存関係が残っていないか |
```

主な作業は1行につき1作業とする。

確認事項は複数存在してよい。論理的に必要な確認を、表を短くする目的で削除しない。

## Step 6: 要注意事項・人間判断を整理する

作業マップの直後に置く。

次を統合して記載する。

- 実装前に人間が決める必要があること
- 前提が未確認のもの
- 外部依存
- 高リスクな作業
- 仕様によって下流設計が変わる事項

該当事項がなければ `なし` と明記する。

## Step 7: 重要な依存・分岐を整理する

L0の最後に置く。

次を必要に応じて示す。

- 先行作業が完了するまで開始できない作業
- 並行可能な作業
- 判断結果によって変わる経路
- 切替・撤去の実施条件

特記すべき依存・分岐がなければ `なし` と明記する。

## Step 8: PythonでL0を構造検証する

L1/L2の確定へ進む前に、必ずL0概要をPythonバリデータへ通す。

```bash
python scripts/validate_overview.py <plan.md>
```

バリデータは少なくとも次を検査する。

- L0のH3が `目的 → 全体作業マップ → 要注意事項・人間判断 → 重要な依存・分岐` の4つだけで、この順序になっている（見出し番号 `0.1` と太字装飾は任意。名称と順序のみ必須）
- 作業マップが `工程 / 主な作業 / 確認事項` の3列である
- 主な作業が空でない
- 明らかに複数作業を1セルへ詰め込んでいない（スラッシュ区切り、`<br>`、セミコロン区切りを粗く検出する）
- 確認事項が空欄でない。なければ `なし` と書かれている
- 要注意事項・人間判断が空欄でない。なければ `なし`
- 重要な依存・分岐がL0の最後にあり、空欄でない。なければ `なし`
- L0が極端に肥大化していない

**FAILの場合はL0を差し戻して修正し、PASSするまでL1/L2の確定へ進まない。**

このスクリプトは構造上の粗い検査のみを担当する。論理的な妥当性はStep 11のPlan Auditで別途確認する。

## Step 9: L1へ作業を展開する

各工程について必要に応じて次を書く。

- 目的
- 前提・開始条件
- 作業手順
- 分岐・例外
- 次工程へ渡すもの
- 確認事項
- 完了条件

完了条件はL1へ置く。L0には独立した完了条件セクションを置かない。

低リスク工程では不要な節を省略してよい。節を残す場合は、特記事項がなくても `なし` と明示する。

## Step 10: L2へ実行詳細を置く

Task詳細は必要に応じて以下を含める。

- Before: 事前確認
- Action: 実施内容
- Touch: 変更・確認対象
- Connect: 他工程・既存経路との接続
- Verify: 検証方法

すべてのTaskへ全項目を強制しない。

## Step 11: Plan Auditを実行する

作成済みPlanを、作成者とは独立したレビュアーの視点で再走査する。

以下を優先して確認する。

1. 目的達成に必要な作業が網羅されているか
2. 工程間の順序・依存が成立するか
3. 作成した成果物が実経路へ接続されるか
4. 正常系・異常系・中断・部分成功・再実行・回帰確認が必要十分か
5. 移行・切替・切り戻しが必要なのに欠けていないか
6. 旧資産・暫定対応が残らないか
7. 重要な暗黙前提がないか
8. 人間判断が必要な事項が隠れていないか
9. 最終状態が当初の目的と一致するか

問題は次の形式で示す。

```text
問題:
必要な理由:
該当工程:
追加・修正先:
```

## Step 12: 監査修正の影響を再検証する

Step 11のPlan AuditによってPlanを修正した場合に実行する。この修正はPlan作成の一部であり、`今回の修正` や `R` IDは付けない。

1. 指摘内容をPlanへ反映する。
2. L0を変更した場合は `scripts/validate_overview.py` を再実行する。
3. 変更した箇所から影響する依存・分岐・前後工程を洗い出す。
4. 影響箇所について、順序・開始条件・接続・検証・切替・復旧条件に新しい矛盾がないか再監査する。
5. 修正によって新しいBLOCKER/WARNINGが生じていないことを確認する。
6. 必要ならStep 11へ戻り、Planが監査を通るまで繰り返す。

監査修正の影響箇所はレビュー中の確認材料として扱い、完成版Planへ修正履歴として残すことは要求しない。

## Step 13: 基準版Planの後続修正を可視化する

一度提示・承認された基準版Planに対し、人間から追加指示・要件変更・前提変更が入った場合に実行する。

1. 修正前の基準版Planを基準に、意味のある変更だけを抽出する。
2. 変更へ `R1`, `R2` ... を割り当て、`今回の修正` 表をPlan先頭へ追加する。
3. 修正版Planの対応箇所へ `[R1]` などを付ける。L0の三列表へ新しい列は追加しない。
4. 文言・表記・整形だけの差分は修正サマリから除外する。
5. L0を変更した場合は `scripts/validate_overview.py` を再実行する。
6. 変更箇所だけでなく、その変更によって影響する依存・分岐・前後工程を再監査する。
7. 修正によって新しいBLOCKER/WARNINGが生じていないことを確認する。

修正サマリは詳細なgit diffの代替ではなく、**人間が基準版からの意味の変化を短時間で確認するための索引**とする。必要なら機械的diffを補助として示してよい。

# 5. 監査の優先度

## BLOCKER

このまま進めるとゴール未達、重大な手戻り、データ不整合、切替失敗につながる可能性が高い欠落。

## WARNING

実行は可能だが、確認・依存・異常系・回帰・復旧などの考慮不足により手戻りが起こり得る状態。

## INFO

監督性・可読性・実行性を高める改善。

# 6. 禁止事項

- L0へ詳細Taskをそのまま大量に並べる
- 行数を減らすために複数作業を1セルへ詰め込む
- 行数を減らすために重要な確認事項を削除する
- 確認事項を空欄にする
- 技術要件一覧を確認事項の代わりにする
- 「実装する」「対応する」だけで作業を終える
- 作成工程はあるが組み込み工程がない
- 正常系だけで完了扱いにする
- 既存経路を置換するのに移行・切替・切り戻しを扱わない
- 未確定事項を推測で埋める
- 監査結果でPlan全文を再要約する
- Plan Audit由来の修正を `今回の修正` に混ぜる
- 意味のある後続修正を文言変更に埋もれさせる
- 修正サマリへ表記変更だけを大量に列挙する
- `R` IDを恒久Task IDとして蓄積する
- 口語的すぎる工程名を多用する
- L0バリデーションがFAILのまま詳細Planを確定する

# 7. 出力スタイル

- 日本語は簡潔かつ業務文書として自然にする
- 主な作業は1行1作業とする
- 工程名の重複を許可する
- 確認事項を主役とし、論理的に必要な事項は削減しない
- 確認事項がない場合は `なし` と明示する
- 大規模計画ではセルを詰めず、L0の作業粒度を上位化する
- 表はL0の全体作業マップを中心に使用する
- 同じ説明をL0/L1/L2で繰り返さない
- 問題箇所には工程またはPhaseを明示する
- 監査中の修正は完成版へ自然に織り込み、修正履歴として表示しない
- 基準版への後続修正では意味のある変更だけを `今回の修正` に集約し、対応箇所へ `R` IDを付ける
- 技術詳細より、作業順序・接続・検証・分岐・復旧を優先する
