# Plan監査ルール

この監査の目的は技術設計そのものを採点することではない。**作業を最後まで完遂するために必要な手順・判断・接続・検証が計画に含まれているか**を確認する。

技術的な細部は必要に応じてL2へ委ねてよい。一方、論理的に必要な確認事項は省略しない。確認事項が存在しない場合も空欄にせず `なし` と明示する。

# 1. 現行把握・影響分析

確認事項:

- 現行の利用フロー・処理フローを把握する工程があるか
- 関連コード、設定、データ、運用、既存テストを確認するか
- 呼び出し元・呼び出し先・共有データ・外部依存を整理するか
- 変更によって影響する既存経路を洗い出すか
- 既存利用者・既存データへの影響を評価するか
- 類似機能や再利用可能な仕組みを確認するか

# 2. 要件・方針確定

確認事項:

- 実装前に確定すべき判断事項が列挙されているか
- 新規追加か既存置換かが明確か
- 一括切替か段階切替かが明確か
- 既存データ・既存利用者の扱いが決まっているか
- エラー時の扱い、再試行、重複実行時の方針が決まっているか
- 未決定事項が仮定や人間判断として明示されているか

# 3. 事前準備

確認事項:

- 必要な権限、環境、設定、テストデータを準備するか
- 実装前に確認可能な期待結果を用意するか
- バックアップや保護措置が必要な場合に計画されているか
- 外部依存の準備完了を確認するか

# 4. 主要変更

確認事項:

- ゴール達成に必要な変更単位が一通り存在するか
- 入力、中心処理、出力、保存、利用側など必要な範囲が欠けていないか
- 周辺変更が主要変更に追随しているか

ここではライブラリ選定や個別APIの書き方までは要求しない。

# 5. 組み込み・接続

最重要監査項目の一つ。

確認事項:

- 新しい処理が実際の利用経路から呼び出されるか
- 出力が次工程へ渡るか
- 新旧データ形式やインターフェースが接続されるか
- 設定・ルーティング・参照先が新経路へ切り替わるか
- エラー結果も利用者・後続工程まで戻るか

# 6. 作業順序・依存

確認事項:

- 前提確認より先に変更へ着手していないか
- 必要な方針決定より先に依存工程が始まっていないか
- 組み込み前にE2E検証を予定していないか
- 移行完了前に切替を予定していないか
- 切替前に旧経路を撤去していないか
- 並行可能な工程と直列必須の工程が区別されているか

# 7. 正常系検証

確認事項:

- 実際の入口から最終結果まで一連の流れを検証するか
- 中間工程を通過したことを確認できるか
- 実結果が当初の目的と一致するか
- 主要な利用パターンを十分に含むか

# 8. 異常系・境界条件

確認事項:

- 不正入力を検証するか
- 外部依存の失敗を検証するか
- 処理途中の失敗を検証するか
- 一部成功・部分失敗を扱うか
- タイムアウト・中断を扱う必要があるか
- 境界値や空データ、大量データなど重要条件を扱うか

# 9. 再実行・重複実行

確認事項:

- 同じ操作を再実行した場合の結果が定義されているか
- 二重実行・重複送信を想定する必要があるか
- 中断後にどこから再開するかが明確か
- 再実行によって重複データや二重処理が発生しないか

# 10. 回帰影響

確認事項:

- 変更対象外の主要機能を再検証するか
- 既存テストを実行するか
- 主要な既存利用フローを再確認するか
- 変更前後の結果比較が必要か

# 11. データ・状態移行

該当する場合のみ必須。

確認事項:

- 既存データ・状態を事前評価するか
- 変換・移行手順があるか
- 移行結果を検証するか
- 一部失敗時の扱いがあるか
- 再実行可能か
- 移行前後の整合性を確認するか

# 12. 切替

新旧経路が存在する場合に確認する。

- 切替前提条件が明確か
- 切替操作が明確か
- 切替直後の確認項目があるか
- 段階展開の場合、次段階へ進む判定条件があるか
- 旧経路停止の条件が明確か

# 13. 切り戻し・復旧

重大な変更では必須。

確認事項:

- 切り戻し条件が定義されているか
- 切り戻し手順があるか
- データ変更を伴う場合に復元可能か
- 手動復旧が必要なケースを把握しているか
- 復旧後に再検証する工程があるか

# 14. 旧資産・暫定対応の撤去

確認事項:

- 旧コード・旧経路を停止または削除するか
- 暫定フラグ・一時設定を撤去するか
- 不要ファイル・デバッグ出力・一時データを除去するか
- 古いドキュメントを更新または廃止するか
- 撤去条件が切替完了後になっているか

# 15. 運用移管・文書化

確認事項:

- 操作方法・運用手順を更新するか
- 監視・確認方法を共有するか
- 障害時の確認・復旧手順を残すか
- 運用担当や関連チームへの周知が必要か
- 変更理由・重要判断を記録するか

# 16. 最終状態確認

確認事項:

- 実利用フローを最終確認するか
- 未解決事項・残課題を明示するか
- 移行・切替・撤去・文書化まで完了しているか
- 作業終了後の状態が当初の目的と一致するか
- 一時的な未完了状態や確認待ちを完了扱いにしていないか

# 17. 暗黙前提

確認事項:

- 必要権限がある前提になっていないか
- 外部サービスへ接続できる前提になっていないか
- 既存データが期待形式である前提になっていないか
- 他チーム・他工程の完了を暗黙に期待していないか
- 検証環境や確認手段が利用可能である前提になっていないか

重要な前提は事前確認、依存事項、未決定事項のいずれかへ昇格する。

# 18. 作業粒度

大きすぎる兆候:

- 一工程に複数の独立した判断・分岐・成果物が混在する
- 途中の確認地点がない
- 失敗時にどこから再開するか分からない

小さすぎる兆候:

- 1ファイル編集や1関数修正がL0の独立工程になっている
- 実装操作の実況になっている
- 全体フローが細部に埋もれている

L0は監督単位、L1は工程単位、L2は実行単位とする。

# 19. L0監督性

L0だけを読んで次に答えられるか確認する。

- 何を達成する計画か
- 完成までにどの作業を通るか
- 現行への影響をどこで整理するか
- 何を実装・変更するか
- どこで実経路へ組み込むか
- どの工程に重要な分岐・失敗条件があるか
- 正常系・異常系・再実行をどこで検証するか
- 移行・切替・切り戻しが必要か
- 完了後に撤去・文書化すべきものがあるか
- 要注意事項・人間判断はどこか
- 重要な依存・分岐は何か
- 詳細を確認すべき高リスク工程はどこか

答えられない場合、詳細が正しくてもPlanアーティファクトとして不十分とする。

# 20. 監査チェックセット

以下は削減用テンプレートではない。該当項目をすべて評価し、L0の確認事項またはL1へ反映する。

```text
[現行・影響]
□ 現行フローと既存挙動を把握する
□ 呼び出し元・呼び出し先・共有データ・外部依存を整理する
□ 影響を受ける既存経路・利用者・データを洗い出す

[判断・準備]
□ 実装前に確定すべき判断事項を明示する
□ 未決定事項・外部依存を明示する
□ 必要な権限・環境・検証データ・保護措置を準備する

[変更・接続]
□ ゴールに必要な主要変更を網羅する
□ 必要な周辺変更を網羅する
□ 新しい成果物を実際の利用経路へ組み込む
□ 既存処理・既存データとの整合を取る

[検証]
□ 正常フローを入口から最終結果まで検証する
□ 不正入力・外部失敗・途中失敗を検証する
□ 一部成功・中断・再実行・重複実行を必要に応じて検証する
□ 既存機能への回帰影響を検証する
□ 実結果が当初の目的と一致することを確認する

[移行・切替]
□ 必要なデータ・状態移行を計画する
□ 移行結果を検証する
□ 新旧切替の前提・手順・直後確認を定義する
□ 切り戻し条件・復旧手順を定義する

[完了]
□ 旧資産・暫定対応の撤去を計画する
□ 運用・文書・関係者への引き継ぎを更新する
□ 未解決事項・残課題を明示する
□ 最終状態が当初の目的と一致することを再確認する
```


# 21. L0表記の完全性

確認事項:

- 全体作業マップの各行が1作業になっているか
- 工程名の重複を不自然に避けるため、複数作業を1セルへ詰め込んでいないか
- 各作業に確認事項が明示されているか
- 確認事項が存在しない場合に `なし` と明記されているか
- 要注意事項・人間判断が作業マップ直後に置かれているか
- 要注意事項・人間判断が存在しない場合に `なし` と明記されているか
- 重要な依存・分岐がL0の最後に置かれているか
- 重要な依存・分岐が存在しない場合に `なし` と明記されているか
- L0が大きすぎる場合、セル圧縮ではなく作業粒度の上位化で調整されているか

これらは `scripts/validate_overview.py` でも粗く検査する。構造検査でFAILしたPlanは詳細化せず、L0へ差し戻す。
