# Simple Plan Auditor

## Purpose

This Skill turns a plan from a long executor-oriented TODO list into a **human-supervisable work artifact**.

It prioritizes three things over low-level implementation detail:

1. A reader can understand the overall flow and important checks from the overview alone.
2. Logically necessary work, decisions, and validation are not omitted.
3. A reader can drill down only into the phases that need closer review.

Always present plans in the order **overview → phase → task detail**.

## When to use

Use this Skill for:

- Planning new features, changes, migrations, investigations, or operational changes
- Reorganizing a large PLAN.md
- Auditing plans generated by AI
- Organizing work that spans multiple phases or components
- Detecting missing steps, dependencies, or checks before execution

Do not use it for trivial work that only needs one to three steps.

# 1. Core Principles

## 1.1 Progressive Disclosure

Organize the plan into three layers:

- **L0: Work Map** — the supervisory view of the whole plan
- **L1: Phase Detail** — expanded detail for a phase that deserves closer review
- **L2: Task Detail** — execution-level detail

Do not place every task in L0.

If L0 becomes too large, **raise the abstraction level of the work shown in L0 instead of packing multiple work items into one cell.** Move the detail to L1.

Do not remove important checks merely to reduce the size of the overview.

## 1.2 Work Map First

The center of L0 is the **Work Map**.

Use this standard three-column form:

| Phase | Main Work | Checks |
|---|---|---|
| ... | ... | ... |

- **Phase**: a higher-level grouping. It may repeat across rows.
- **Main Work**: one work item that a human should be able to judge for omission. Use one work item per row.
- **Checks**: logical conditions that must be verified for the work to be sound.

Phase names do not need to be unique. Repeat the same phase name when several work items belong to it.

## 1.3 Check First

The most important part of this Skill is the **Checks** column.

Technical implementation details may be delegated to the AI, but logically necessary checks must not be omitted.

When applicable, always consider:

- Understanding current behavior and existing flows
- Scope of impact and dependencies
- Decisions that must be made before implementation
- Work order and start conditions
- Whether new work is actually wired into the real usage path
- Happy path, failure path, interruption, and partial success
- Retry and duplicate execution
- Regression impact on existing behavior
- Data or state migration
- Cutover and rollback
- Removal of obsolete or temporary assets
- Operations and handoff
- Whether the final state actually matches the objective

If there is genuinely nothing to check, do not leave the cell blank. Write **`None`** explicitly.

Blank cells are not distinguishable from missed review.

## 1.4 Human Review Granularity

Choose granularity based on **what a human needs to inspect for possible omission**, not on implementation units.

Good L0 candidates include:

- Current-state review and impact analysis
- Requirement and policy decisions
- Major changes
- Wiring into existing usage paths
- Data migration
- Integrated validation
- Cutover
- Operational handoff
- Removal of obsolete or temporary assets

Too fine-grained for L0:

- Implementing one function
- Editing one file
- Specific library API calls
- Low-level type-definition details

Place those in L1 or L2 when needed.

## 1.5 One Work Item Per Row

Use one main work item per row.

Good:

```markdown
| Current-state review & impact analysis | Map the current user flow | Are there any overlooked entry points? |
| Current-state review & impact analysis | Map dependencies and shared data | Are there hidden dependencies? |
```

Avoid:

```markdown
| Current-state review & impact analysis | Map the current flow / dependencies / shared data / change impact | ... |
```

For large plans, raise the abstraction level instead of compressing many independent actions into one row.

## 1.6 Flow and Wiring

Do not stop a phase at “create” or “implement.”

Always check the end-to-end chain:

```text
Clarify prerequisites
  ↓
Implement / change
  ↓
Wire into existing paths
  ↓
Integrated validation
  ↓
Migration / cutover
  ↓
Operational verification
  ↓
Cleanup / final verification
```

A deliverable is incomplete if it is created but never connected to the path where it is actually used.

## 1.7 Unknown Is Valid

Do not invent answers for unresolved items.

Treat these as valid explicit states:

- Undecided
- Needs verification
- Assumption
- External dependency
- Blocker
- Human decision required

Promote important unresolved items into `Cautions & Human Decisions`.

# 2. L0 Structure

Use the following order for the overview:

1. **Objective**
2. **Work Map**
3. **Cautions & Human Decisions**
4. **Key Dependencies & Branches**

`Key Dependencies & Branches` must be the final section in L0.

Do not add a standalone completion-criteria section to L0. Final checks required for success should be represented in the Work Map and in L1 validation.

Use [references/PLAN_FORMAT.md](references/PLAN_FORMAT.md) for the detailed format.

# 3. Writing Style

Write clear, professional planning language.

Prefer concise noun phrases for phase labels and concise action-oriented business language for work items.

Examples:

- `Check current state` → `Current-state review & impact analysis`
- `Look at what this affects` → `Map the current flow and change impact`
- `Build the base` → `Prepare shared foundation`
- `Try failure cases` → `Validate failure and retry conditions`
- `Make sure nothing broke` → `Validate regression impact`
- `How to undo it` → `Rollback procedure`
- `Clean things up` → `Remove obsolete and temporary assets`

Avoid slang or overly casual phase names, but do not drift into bureaucratic language.

# 4. Planning Workflow

## Step 1: Fix the objective

In one to three sentences, state what becomes possible or what changes after the work is complete.

## Step 2: Enumerate required work

List everything required to reach the objective without worrying about presentation granularity yet.

Use [references/AUDIT_RULES.md](references/AUDIT_RULES.md) as the audit lens.

## Step 3: Add checks to each work item

Before focusing on implementation detail, ask:

- What must be true for this work to be considered successful?
- Is anything missing between the previous and next phase?
- What important branches, failures, or retry conditions exist?
- What does this change affect in the existing system or workflow?
- What must a human decide beforehand?

If there is nothing to check, write `None`.

## Step 4: Adjust granularity for L0

If L0 is too large, do not combine many independent tasks into one cell.

Instead, raise the abstraction level of the work represented in L0.

Do not collapse together work that has:

- Different important decisions
- Important happy-path / failure-path branching
- Migration, cutover, or rollback
- Independent external dependencies
- High-risk data or state changes
- Work that humans need to supervise separately

## Step 5: Build the Work Map

Create the three-column table:

```markdown
| Phase | Main Work | Checks |
|---|---|---|
| Current-state review & impact analysis | Map the current user flow | Are there any overlooked entry points? |
| Current-state review & impact analysis | Map dependencies and shared data | Are there hidden dependencies? |
```

Use one main work item per row.

A row may contain multiple logical checks. Do not remove necessary checks merely to keep the table short.

## Step 6: Organize cautions and human decisions

Place this immediately after the Work Map.

Combine and surface:

- Decisions humans must make before implementation
- Unverified assumptions
- External dependencies
- High-risk work
- Decisions that change downstream design

If none exist, write `None` explicitly.

## Step 7: Organize key dependencies and branches

Place this at the end of L0.

Show when relevant:

- Work that cannot start until prerequisite work is complete
- Work that can proceed in parallel
- Paths that depend on a decision outcome
- Conditions for cutover or cleanup

If there are no noteworthy dependencies or branches, write `None`.

## Step 8: Validate L0 structure with Python

Before finalizing L1/L2, run the L0 overview through the validator:

```bash
python scripts/validate_overview.py <plan.md>
```

The validator checks at least:

- L0 contains exactly these H3 sections in this order: `Objective → Work Map → Cautions & Human Decisions → Key Dependencies & Branches` (numbering such as `0.1` and bold styling are optional; names and order are required)
- The Work Map has exactly three columns: `Phase / Main Work / Checks`
- Main Work is not blank
- Main Work does not obviously pack several work items into one cell
- Checks is not blank; use `None` if there is nothing to check
- Cautions & Human Decisions is not blank; use `None` if there are none
- Key Dependencies & Branches is the final L0 section and is not blank; use `None` if there are none
- L0 has not become excessively large

**If validation fails, revise L0 and rerun validation. Do not finalize L1/L2 until it passes.**

This script only performs coarse structural checks. Logical correctness is reviewed separately in Step 11.

## Step 9: Expand work into L1

For each phase, include as needed:

- Objective
- Preconditions / start conditions
- Work steps
- Branches / exceptions
- Outputs for the next phase
- Checks
- Completion criteria

Completion criteria belong in L1, not in a standalone L0 section.

Low-risk phases may omit unnecessary subsections. If a subsection is retained and has nothing noteworthy, write `None` rather than leaving it blank.

## Step 10: Add L2 execution detail

Task detail may include:

- Before: pre-checks
- Action: what to do
- Touch: what is changed or inspected
- Connect: how it connects to other phases or existing paths
- Verify: how to verify it

Do not force every task to contain every field.

## Step 11: Run Plan Audit

Re-read the completed plan from the perspective of an independent reviewer rather than the original planner.

Prioritize these questions:

1. Does the plan cover all work required to achieve the objective?
2. Are phase order and dependencies valid?
3. Are created outputs actually connected to real usage paths?
4. Are happy path, failure path, interruption, partial success, retries, and regression checks sufficient where needed?
5. Are migration, cutover, and rollback missing where they are required?
6. Will obsolete or temporary assets remain afterward?
7. Are there important hidden assumptions?
8. Are human decisions hidden inside implementation detail?
9. Does the final state match the original objective?

Report issues in this form:

```text
Issue:
Why it matters:
Affected phase:
Where to add or revise:
```

# 5. Audit Severity

## BLOCKER

A gap likely to cause failure to reach the goal, major rework, data inconsistency, or cutover failure.

## WARNING

The work may still execute, but weak handling of checks, dependencies, failures, regression, or recovery can cause rework.

## INFO

An improvement that increases supervision quality, readability, or executability.

# 6. Prohibited Patterns

- Dumping large numbers of detailed tasks directly into L0
- Packing multiple independent work items into one cell just to reduce row count
- Removing important checks just to shorten the overview
- Leaving Checks blank
- Replacing logical checks with a list of technical requirements
- Ending a work item at “implement” or “support” without downstream connection
- Creating new behavior without a wiring/integration step
- Treating the happy path alone as completion
- Replacing an existing path without addressing migration, cutover, and rollback where needed
- Guessing unresolved requirements
- Re-summarizing the entire plan in the audit result
- Using overly casual phase names
- Finalizing detailed planning while L0 validation is failing

# 7. Output Style

- Use concise, professional English
- Keep one main work item per row
- Allow phase names to repeat
- Treat Checks as the primary review surface and do not remove logically necessary checks
- Write `None` when there is genuinely nothing to check
- For large plans, raise L0 abstraction instead of packing cells
- Use tables mainly for the L0 Work Map
- Do not repeat the same explanation at L0, L1, and L2
- Identify the affected phase when reporting problems
- Prioritize work order, wiring, validation, branching, and recovery over low-level technical detail
